## 2026-10-15 변경

### 개발 역할과 저장소

- 사용자 요청으로 개발 역할을 바꿨다. **Claude가 기획·구현·시험·문서를 맡고, Codex는 읽기 전용 검토만 한다.** 기획서 23.1절과 README에 반영했다. 아래 이전 기록의 ‘Claude의 UI’, ‘reviewer’ 표현은 당시 분담 그대로 둔다.
- 이 폴더에 별도 git 저장소를 만들었다(`main`, 커밋 없음). 기존에는 홈 폴더 저장소 안에 있었고, 그 저장소는 건드리지 않았다.
- 기준선(이전 단계 코드 전체) Codex code 리뷰에서 실제로 재현되는 결함 2개가 나왔다. ① 하위 `.gitignore`에서 `!foo/`로 다시 포함한 폴더의 파일이 계속 제외된다(`files.ts`의 `ignored()`가 `.gitignore`마다 부모 폴더 판정을 따로 물려받음). 실제 git으로도 해당 파일이 제외 대상이 아님을 확인했다. 제외를 더 많이 하는 쪽의 오류였다. ② 함수를 바로 반환하는 화살표 함수(`() => () => 42`)의 반환 단계가 빠졌다. 둘 다 **수정**했다.
- ①의 수정(사용자 승인한 방식): `ignore` 패키지의 공개 `test()`는 각 `.gitignore`의 판정을 부모 폴더에도 따로 적용한다. 탐색과 `assertAllowed()`는 이미 폴더를 한 단계씩 검사하며 제외된 폴더에서 멈추므로, 각 `.gitignore`는 경로 자신만 판정하면 된다. 이 판정은 ignore@7.0.12(고정 버전)의 내부 함수 `_rules.test`를 쓴다. 공개 API가 아니므로 함수가 없으면 열지 않고 실패한다. 회귀 검사는 재포함 폴더의 파일 허용, 그 안의 `*.txt`(읽기 지원 형식이라 `.gitignore` 규칙만으로 가려짐)·재포함하지 않은 폴더의 계속 제외를 탐색과 읽기 양쪽에서 확인하고, 같은 폴더를 실제 `git status --ignored` 결과와 대조한다. 패키지 버전을 올리면 이 검사로 동작을 다시 확인해야 한다.

### 흐름 따라가기 화면

함수 하나를 **코드에 적힌 순서대로** 한 단계씩 따라가는 화면을 만들었다. AI 없이 Tree-sitter로 확인한 구조만 쓴다. 구현 기획은 Codex plan 리뷰 4회 끝에 통과했다(함수 끝 추론 문구 제거, throw를 ‘끝나는 곳’으로 부르지 않기, 빈 if·else-if·중괄호 없는 중첩 if의 연결 규칙 보완).

- 분석(`syntax.ts`): 단계마다 `detail`(if·반복 조건, for-of 항목, switch·case 값, return·throw 대상, 최대 300자)과 if 단계의 `branch`(맞으면·아니면 이어지는 단계 ID)를 추가했다. 연결은 같은 문장 목록(블록·case) 안의 다음 단계까지만 계산하고, 반복의 다음 회차·함수 끝·블록 밖 이동은 계산하지 않고 null로 둔다. 화살표 함수의 식 본문은 `expression_body` 단계다. 함수에는 매개변수 원문 `params`를 추가했다.
- 화면(`flow.tsx`): 함수 요약(받는 값, 반환·오류 던지기 위치, 목적은 AI 연결 전이라 미확인), 번호 붙은 단계 목록, 단계 카드(지금 하는 일, 조건·값, 맞으면/아니면 이동, 실제 코드 조각, 이전/다음/코드 크게 보기). 반복문·함수 호출에는 되풀이·연결 미확인 안내를 붙인다. 함수가 실제로 어디서 끝나는지는 확인하지 않았다고 표시한다.
- 단계 이동은 기존 `readEvidence`로 main이 해시·범위를 다시 확인한 뒤 표시한다. 코드가 바뀌면 코드 조각을 숨기고 모든 이동을 잠근다.
- 코드 읽기에서 고른 함수·단계가 흐름에서도 이어지고, ‘이 함수 흐름으로 보기’로 돌아올 수 있다. 흐름 보기에서 파일을 고르면 흐름 보기에 머문다.
- 커밋 전 Codex code 리뷰 지적을 반영했다. 함수 안 클래스 본문(인스턴스 필드 초기화 등)은 그 함수가 지날 때 실행되지 않으므로 단계에서 뺐다(함수 본문처럼 건너뜀, 이때 실행되는 static 초기화도 표시하지 않음). return·try 문구는 finally가 결과·흐름을 바꿀 수 있고 catch는 있을 때만 간다고 고쳤다. throw 문구는 catch·finally 순서를 단정하지 않는다(catch 안에서 다시 던진 오류는 그 catch가 받지 않음). do…while은 적어도 한 번 들어간다고 따로 안내한다.

### 한눈에 보기: 문서 소개와 학습 시작점 후보

1A의 ‘확인한 근거에 따른 개요·시작점’을 AI 없이 채웠다. 구현 기획은 Codex plan 리뷰 3차에 통과했다(확장자 없는 README는 정책상 제외라 지원 범위에서 뺌, 코드·HTML 블록 안 글을 소개로 고르지 않음, 개요의 최신성 표시 분리).

- 분석(`overview.ts`): 폴더를 열 때 worker가 scan 직후 계산한다(새 IPC 없음). 루트 `README.md`·`README.txt`에서 첫 제목과 첫 산문 문단(최대 400자)을 줄 번호와 함께 뽑는다. 코드 울타리(같은 문자·충분한 길이로만 닫힘)·들여쓴 코드(덜 들여쓴 줄에서 끝남)·HTML 블록(CommonMark 4.6의 블록 태그·태그만 있는 줄, 닫는 표시가 필요한 종류는 빈 줄을 넘어 이어짐)·배지·표는 건너뛴다. 문장을 시작하는 인라인 태그와 자동 링크는 소개 글로 남긴다. 시작점 후보는 `package.json` main·bin 대상 → 이름이 index·main·app인 파일 → 나머지 TS/JS 파일 순으로 최대 20개 파일을 읽어 export된 함수, 또는 export 함수가 없는 시작 파일(main·bin 대상, index·main·app) 자체를 합쳐 최대 8개 고른다. 파일 후보는 함수를 자동으로 고르지 않고 파일만 연다. 파일은 `readAllowed`로 텍스트만 읽고 실행하지 않는다. 제외되었거나 프로젝트 밖을 가리키는 `package.json` 대상, 깨진 JSON, 읽지 못한 파일은 메모로 알린다.

### AI로 보내기 전 비밀값 가리기

기획서 16.3절의 ‘허용 소스 안의 비밀값 전송 전 검사·마스킹’을 구현했다. **실제 AI 전송은 여전히 main에서 막혀 있으며 바꾸지 않았다.** 구현 기획은 Codex plan 리뷰 1차에 통과했다.

- `src/core/ai/secrets.ts`의 `maskSecrets()`: 정밀도가 높은 형태만 찾는다. 개인키 블록(끝 표시가 없으면 끝까지), AWS 액세스 키 ID, GitHub 토큰, `sk-` 키, Google API 키, Slack·Stripe 토큰, JWT, `scheme://user:비밀번호@host`의 비밀번호, password·passwd·secret·token·api key·access key·private key 이름에 대입한 4자 이상 따옴표 문자열, 같은 이름의 한 줄 설정 값(`password: …`, `TOKEN=…`). 가린 자리는 `[MASKED_SECRET]`·`[MASKED_PRIVATE_KEY]`이고 줄 수를 유지한다. 문자열은 시작한 따옴표로만 끝나며 다른 따옴표·이스케이프·백슬래시 줄 이음은 내용으로 본다. 앞 규칙이 이미 가린 값은 다시 세지 않는다.
- 성능 방어: main 프로세스에서 최대 32 KiB 파일마다 동기로 돌기 때문에, 긴 덩어리 뒤에서 실패할 수 있는 패턴은 덩어리 맨 앞에서만 시작하고(lookbehind), 키 이름은 한 번 읽은 뒤 비밀 단어를 따로 검사한다. 고치기 전 패턴은 `token`을 반복한 32 KiB 한 줄에서 5분이 넘도록 끝나지 않았다(직접 측정, Codex 리뷰도 4 KiB에서 2.9초 재현).
- 적용 지점은 `workflow.ts`가 프롬프트 자료를 만드는 곳 하나다. 선택 코드와 관련 파일 전체 코드의 사본만 가리고, `revalidate`가 원본과 파일을 비교할 수 있게 snapshot의 원본은 그대로 둔다. organizing 뒤에 추가되는 관련 파일도 단계마다 다시 가린다. AI는 근거를 ID로만 가리키므로 가린 텍스트의 위치는 쓰지 않는다.
- 가린 파일마다 ‘비밀값처럼 보이는 N곳을 가린 뒤 보냈어요 … 모든 비밀값을 찾아낸다고 보장하지는 않아요’를 AI 자료와 답변의 ‘읽기 범위’에 넣는다. 전송 동의 문구에도 같은 한계를 적었다.
- 한계: 엔트로피 추측 탐지 없음, 따옴표 없는 코드 대입(`token = req.headers…`)·비교식(`password === "…"`)·사용자가 직접 쓴 질문은 검사하지 않음. 비밀처럼 보이는 이름의 일반 값(`tokenType = "Bearer"`)도 가리는 오탐을 허용한다.

### Antigravity(agy) 앱 전용 HOME (사용자 선택 A안)

agy 1.3.5에는 설정 위치를 바꾸는 공식 옵션이 없다(공식 CLI reference·install 문서, 도움말 확인). 설정·`GEMINI.md`·MCP·플러그인·훅이 `~/.gemini` 아래에 있고 로그인은 OS 키체인을 쓴다고 문서에 적혀 있다. 사용자가 2026-10-15 A안을 골랐다: agy를 켤 때 `HOME`을 앱 전용 폴더(`<userData>/agy-home`)로 바꾼다. **공식 기능이 아니므로 agy 업데이트로 깨질 수 있다.** 구현 기획은 Codex plan 리뷰 4차에 통과했다.

- `LocalAiRuntime`이 앱 전용 agy 홈을 두 번째 인자로 받고, Codex 홈과 같은 준비(생성·링크 거절·0700, 실패 시 미실행)를 한 뒤 agy 자식 환경에만 `HOME=<agy-home>`을 준다. claude-code에는 바꾸지 않는다.
- **실행 인자 교정**: 기존 후보 `-p --model …`는 agy 1.3.5에서 종료 코드 2로 실패했다("-p took --model as its prompt"). `-p`는 바로 뒤 글을 질문으로 받기 때문에, 코드를 명령줄에 넣지 않도록(16.4절) 공식 headless 문서의 `--input-format stream-json --output-format stream-json`으로 바꾸고 질문을 표준입력 한 줄(`{"event":"user",…}`)로 보낸다. 최종 인자: `--input-format stream-json --output-format stream-json --model gemini-3.8-flash-high --mode plan --sandbox --print-timeout 2m`.

### C04 실제 실행 울타리(sandbox-exec)

사용자가 2026-10-17 기획·구현·실제 계정 요청(최대 6건)을 승인했다. 구현 기획은 Codex plan 리뷰 2차에 통과했다. 지금까지는 도구를 빼앗는 것이 유일한 벽이었다. 이번에 **도구 제한이 뚫려도 홈·`/Users`·`/Volumes`의 파일 읽기와 허용한 폴더 밖 쓰기를 막는 두 번째 벽**을 더했다. 홈 밖 파일 읽기, 자기 앱 전용 홈의 읽기·쓰기, 네트워크, Keychain 서비스는 막지 않는다(아래 ‘남는 한계’). 보안 빈칸 조사 3번, 기획서 16.2절에 해당한다.

- **AI 질문 단계는 `/usr/bin/sandbox-exec -p <규칙> <CLI> …`로 실행한다**(`src/core/ai/fence.ts`, `runtime.ts`의 `executeVerifiedStage`). 설치 확인(`--version`)은 질문·코드를 보내지 않으므로 울타리 없이 둔다(2026-10-18부터는 Codex·agy의 설치 확인도 울타리 안이다. 아래 ‘판정 규칙·설치 확인 울타리·agy MCP 설정’).
- **규칙**(뒤 규칙이 앞 규칙을 덮는다):
  - 시작은 `allow default`다.
  - 홈·`/Users`·`/Volumes`의 파일 내용 읽기와 폴더 목록 읽기(`file-read-data`)를 막는다. 경로 해석에 필요한 메타데이터는 막지 않는다.
  - 다시 허용하는 것: 이 CLI의 앱 전용 홈, 이번 실행 임시 폴더, CLI 실행 파일, Node 스크립트의 npm 패키지 폴더.
  - 쓰기는 앱 전용 홈, 실행 임시 폴더, `/dev/null`만 허용한다.
  - Codex는 agy 홈을, agy는 Codex 홈을 읽지 못한다.
  - `TMPDIR`은 실행 임시 폴더로 바꾼다.
- **패키지 폴더는 경로에 `node_modules` 단계가 있을 때만 인정한다.** 홈에 놓인 `package.json`이 홈 전체를 다시 여는 일을 막는다(plan 리뷰 지적).
- **울타리를 씌울 수 없으면 AI를 실행하지 않는다.** macOS가 아니거나, `sandbox-exec`가 없거나, 패키지 폴더를 찾지 못하면 `AI_UNAVAILABLE`이다. sandbox-exec가 규칙 적용에 실패해 비정상 종료해도 울타리 없이 다시 실행하지 않는다.
- **시험(계정 없음):**
  - `tests/ai-fence.test.ts`: 규칙 문자열, 경로 따옴표·거절, 패키지 폴더 계산을 확인한다. 실제 sandbox-exec에서 가짜 홈의 비밀 파일 읽기, 홈 목록, 실제 홈 목록, 다른 CLI 홈 읽기, 홈·임시 폴더 밖 쓰기가 막히는지도 본다(EPERM/EACCES). 자기 홈 읽기·쓰기, 실행 폴더 쓰기, 패키지 읽기는 허용되는지 확인한다.
  - `tests/ai-runtime.test.ts`: 단계 실행이 sandbox-exec로 시작하는지, 실패 세 경우에 CLI를 직접 실행하지 않는지 확인한다.
  - 로컬 Codex 탐침(`codex-probe.ts`)은 앱 울타리를 벗기고 시험용 규칙으로 실행한다. 울타리 안에 울타리를 또 씌울 수 없어서다. 시험용 규칙은 네트워크와 인증 관련 경로를 따로 막으며, 앱 울타리처럼 홈 전체를 막지는 않는다.

### Codex 강제 호출 시험 (C08 local, 2026-10-18)

사용자가 남은 빈칸을 더 시험하기로 했다(B안). 실제 모델은 시켜도 금지 도구를 시도하지 않아, Codex 7칸은 모두 ‘시도 없음’이었다. 그래서 **로컬 가짜 서버가 도구 호출을 직접 보내고**, 앱과 같은 실행 인자의 진짜 Codex 0.163.0이 어떻게 처리하는지 봤다. 실제 계정 요청과 외부 망 접속은 0건이다. 구현 기획은 Codex plan 리뷰 지적(빠진 도구 이름, 앱 거절과 시험 결과 분리, 거절 출처 판정, 버전·모델 확인)을 반영했다.

- **왜 필요한가(공식 소스 rust-v0.163.0):**
  - `core/src/tools/registry.rs`는 **등록된 도구라면 모델에게 보여 주지 않았어도 이름만으로 실행한다.** 그래서 ‘제공 목록에 없음’은 ‘실행 불가’가 아니다.
  - `apply_patch`는 모델 정보에 패치 형식이 있으면 등록된다(`gpt-6.1-sol`은 `freeform`). 앱의 `excluded_tool_namespaces`는 Code Mode 노출만 거른다.
  - MCP 자료 도구 3개는 `code_mode_only` 모델에서 MCP 서버가 없어도 등록된다.
- **방식(`tests/live/codex-probe.ts`의 `forced-calls`, `tests/live/codex.live.ts`의 `C08 local`):**

### Codex 교차검증 반영: 이미지 생성·기록 노트 끄기, 로그인 모델 정보 확인 (2026-10-18)

사용자가 남은 빈칸을 별도 Codex 세션에 다시 조사하게 했다(읽기 전용, 실제 계정 요청 0건). 새 발견 4개를 공식 소스(rust-v0.163.0)와 결과 파일로 다시 확인했고, 모두 맞았다. 사용자가 추천대로 진행하도록 승인했다.

- **이미지 생성 도구가 꺼져 있지 않았다.** `image_generation`은 기본 켜짐이다(`features/src/lib.rs`). 기능이 켜져 있고, 무료 요금제가 아니고, 제공자가 지원하고, 모델이 이미지 입력을 받고, OpenAI 인증이면 `image_gen.imagegen`이 등록된다(`core/src/tools/spec_plan.rs` `image_generation_available`). `excluded_tool_namespaces`로는 막히지 않는다.
- **기록·노트 도구 9개가 켜질 수 있다**(기록 4개, 노트 5개, 노트 쓰기·덧붙이기 포함, `ext/history-notes`). 조건은 OpenAI 제공자, Codex 백엔드 인증, 그리고 `token_budget.use_history_notes_extension`이다. 이 값이 켜지는 경로는 두 가지다(`core/src/session/token_budget.rs`):
  - 모델 정보의 기본값(`apply_model_defaults`). 사용자가 `token_budget`을 명시하면 적용하지 않는다.
  - `context_management` 기능(`apply_experimental_context`, 기본 꺼짐). 켜져 있고 모델이 `supports_experimental_context`이고 대상 요금제면, 명시한 `token_budget` 끄기를 다시 켜고 기록·노트를 켠다(security 검토 제안으로 확인).
- **로그인 상태의 모델 정보(사용자 승인, 도구 관련 값만 읽음):** 앱 전용 Codex 홈의 `models_cache.json`은 로그인 상태에서 서버가 준 모델 목록이다. 계정 식별 정보(`identity`)와 `etag`는 열지 않았다.
  - 받은 시각 2026-10-17, 클라이언트 0.163.0, 모델 9개.
  - 기본 모델(우선순위 1) `gpt-6.1-sol`: `code_mode_only`, 패치 `freeform`, 셸 `unified_exec`, 입력 텍스트·이미지, `token_budget` 꺼짐·기록 노트 꺼짐.
  - 번들 시험 자료와 다른 도구 관련 값은 셸 방식(`shell_command` → `unified_exec`)뿐이다. 셸은 `--disable shell_tool`로 꺼져 있다. 도구 설명 항목은 같았다.
  - `gpt-6.1-sol`의 `supports_experimental_context`는 `false`다(다른 모델 중에는 `true`도 있다).
  - 그래서 **확인한 모델 정보만으로는** 기록·노트가 켜지지 않는다. 모델 목록은 서버에서 다시 받으면 바뀔 수 있고, 관리형 설정까지 확인한 것은 아니다. 이미지 생성은 유료 요금제라면 켜질 조건을 갖췄다(사용자 요금제는 확인하지 않음).
- **앱 실행 인자에 `--disable image_generation`, `--disable token_budget`, `--disable context_management`를 더했다.** 사용자는 이미지 생성과 기록·노트 끄기를 승인했다. 세 번째 옵션은 같은 목적의 두 번째 경로를 막으려고 더했다. 로컬 C05·C07·C08에서 Codex가 세 옵션을 받아들였고, 제공 도구 목록은 전과 같았다. 로그인 조건에서 옵션이 받아들여지는지, 그리고 도구가 실제로 빠지는지는 **실제 요청으로 아직 확인하지 않았다.**
- **agy도 가짜 서버로 시험할 수 있다.** 공식 설치 문서에 API 키 방식(`settings.json`의 `"modelProvider": "gemini"`, `GEMINI_API_KEY`)과 다른 끝점(`GOOGLE_GEMINI_BASE_URL`)이 있다([공식 문서](https://antigravity.google/docs/install?tab=cli#point-the-cli-to-a-custom-endpoint)). 앞서 쓴 인계서의 "공식 끝점 설정이 없다"는 틀렸다. #### 2단계 추가: 남은 선언 도구 7개 (2026-10-18)

사용자가 남은 7개도 시험하기로 했고, 완전한 정리 증명이 불가능한 한계를 받아들여 "이 컴퓨터에서, 정리 완전성 미확인 표시"를 골랐다. 기획은 Codex plan 리뷰 3차에 통과했다.

- **고정 인자(위험한 값 제외):** `manage_task`(`status`, 없는 작업), `manage_subagents`(`list`), `send_message`(없는 받는 사람), `schedule`(1회·60초·데몬 아님), `define_subagent`(도구 없는 정의), `invoke_subagent`(가짜 서버만 쓰는 하위 에이전트 1개), `ask_question`(질문 1개). `kill`·`kill_all`·`send_input`은 보내지 않는다. `replace_file_content`를 안쪽에도 보내 호출은 모두 18개다. 공식 [hooks 문서](https://antigravity.google/docs/hooks/)는 앞의 셋을 agy 자신의 작업·에이전트 사이 통신으로 설명한다. 하지만 `schedule`의 지속 여부, 정의 저장 위치, 하위 에이전트의 별도 프로세스 여부·훅 상속은 문서에 없다. 그래서 문서를 믿지 않고 sandbox로 가둔다.
- **시험용 sandbox에 더한 것:** 같은 sandbox 밖 프로세스에 신호 금지, `launchctl`·`crontab`·`at`·`batch` 실행 금지, 모든 Mach 서비스 조회 금지(XPC로 일을 맡기는 경로 차단). 모든 Mach 조회를 막아도 agy는 정상 답변했다. 단위 시험: 밖 프로세스 신호 EPERM·자기 자식은 허용, 예약 도구 EPERM, `notifyutil` 실패, 자식 셸도 같은 제한.
- **남는 프로세스:** 시험의 `runProcess` 감싸기가, 런타임이 작업 폴더를 지우기 **전에** 자손(100ms 표본의 자식·손자·같은 그룹)을 끝내고 작업 폴더를 한 번 더 확인한다. 신호마다 직전에 시작 시각을 다시 확인한다. 표본 사이에 떨어져 나간 자식은 놓칠 수 있어 결과에 `completeness: unverified`를 남긴다(정리 완전성 미확인). 남은 것이 있어도 위 sandbox 안이라 쓰기·연결·신호·예약·시스템 서비스가 막힌다.
- **본 대화만 호출을 받는다:** 대화 기록이 지금까지 보낸 호출과 정확히 맞고 마지막 호출의 응답이 있는 요청만 다음 호출을 받는다(하위 에이전트는 부모 기록을 물려받지 않는다: [subagents](https://antigravity.google/docs/subagents/)). 그 밖의 모델 요청은 `unknown-origin`으로 세고 시험을 실패시킨다.
- **결과(agy 1.4.2, 통과):**
  - **18개 모두 앱 훅에 거절됐다.** 16개는 도구 단계의 거절 형식으로 확인했다. `invoke_subagent`·`ask_question` 2개는 agy가 도구가 아닌 단계(`subagent`, 이름 없는 `unknown`)로 보고했다. 그 단계는 모두 ERROR로 끝났고, agy가 모델에게 돌려준 응답에 앱 훅의 정확한 거절 문장이 있었다. 이 2개는 응답을 근거로 거절로 기록했다(`evidence: response`).
  - `invoke_subagent`는 도구 단계로 시작했다가 같은 단계를 `subagent` 단계로 바꿔 끝낸다. 그래서 단계마다 종류와 상관없이 마지막 상태를 본다(`agyAttempts`). 도구가 아닌 단계는 끝나면 실행, 그 밖은 판정 불가로 센다. 로그인 시험 A5~A7에도 같은 규칙이 적용되어 더 엄격해진다.
  - 실행 흔적 0(파일 변화·canary 유출·가짜 주소 요청·끝난 다른 단계 없음), `unknown-origin` 0, 본 대화 요청 19건(호출 18 + 마지막 답), 남은 자손 0(본 것 1~3, 완전성 미확인).
  - 종류별 요약(`local-api-key`): 읽기·편집(밖·안)·셸·웹 **`blocked`**, MCP `not-attempted`(이 방식에는 MCP 선언이 없다. 로그인 조건의 MCP는 A7에서 `blocked`).
- **검토 반영(code·security 1차):**
  - 자손 추적은 첫 프로세스와 각 자손의 **번호와 시작 시각을 함께** 기억한다. 번호가 다른 프로그램에 재사용되면 그 프로그램과 자식은 넣지 않는다. 그룹은 첫 프로세스가 같은 프로세스이거나 사라졌을 때만 맞춘다(POSIX는 같은 번호의 그룹이 있는 동안 그 번호를 재사용하지 않는다).
  - 본 대화 판별은 대화 기록의 호출 **전체를 순서대로** 보낸 호출과 비교하고, 마지막 호출의 응답을 id 또는 같은 이름 순번으로 확인한다.
  - 응답을 근거로 한 거절은 agy가 실제로 돌려준 거절 응답의 **정확한 모양**일 때만 인정한다: `output` 필드 하나, 값이 `Created At: …` / `Completed At: …` / `Encountered error in tool execution: tool call denied by pre-tool hook: <앱 훅 이유>`. 거절 문장을 인용한 성공 결과, 다른 필드가 섞인 응답, 다른 틀은 인정하지 않는다.
  - 어떤 거절된 호출로도 설명되지 않는 다른 종류의 단계(ERROR)는 판정 불가, 끝난 단계(DONE)는 실행으로 남아 시험 전체와 종류별 요약을 함께 실패시킨다(`kindAttempts`). 거절과 짝지을 수 있는 것은 ERROR로 끝난 단계뿐이고, 아직 진행 중인 단계는 판정 불가로 남는다(code 2차 검토 지적).
  - 이 기준으로 다시 실행해도 결과는 같았다(18개 모두 앱 훅 거절, 종류별 `blocked`).
- **새로 찾은 앱 방어의 빈틈(사용자 결정 대기):** 앱의 `parseStageOutput`은 agy의 `step_type === 'tool'`만 보고 답을 버린다. 그래서 agy가 하위 에이전트나 질문을 `subagent`·`unknown` 단계로만 보고하면 앱은 답을 받아들일 수 있다. 이번에는 훅이 막아 피해는 없었다. 정상 답변의 단계 종류는 `user_input`·`agent_response`뿐이었다(A8, API 키 방식). 그 둘만 허용하도록 바꾸는 것은 앱 정책 변경이라 승인 후에 하고, 로그인 방식의 정상 답변도 같은지 실제 요청 1건으로 확인해야 한다.
- **범위:** API 키 방식·임시 홈·시험용 sandbox 조건이다. 로그인 방식의 증거가 아니며 A6·A7·C04 판정과 섞지 않는다.

### 후속 질문의 관련 파일 근거 재현 (A01, 2026-10-18)

Codex 전체 검수 계획의 A01이다. 기존 후속 대화 시험은 관련 파일 근거 객체를 고정해 다시 썼다. 실제 앱은 파일을 읽을 때마다 새 근거 ID를 만든다. 그래서 실제 `ProjectAiContext`와, 프롬프트 JSON만 읽는 가짜 모델로 다시 재현했다(`tests/ai-followup.test.ts`, 4개). 시험은 이전 ID를 새 ID로 몰래 바꿔 주지 않는다. CLI·계정·네트워크는 쓰지 않았다.

- **모델이 관련 파일을 다시 요청할 때:** `b.ts`가 새 ID를 받고 답이 그 ID를 인용하면 표시된다. 새 ID는 앱 조회에서 같은 파일로 이어지고, 질문 기준(처음 고른 범위)은 그대로다. 모델에게 보낸 이전 답변 기록의 ID는 고쳐 쓰지 않는다.
- **모델이 이전 답변의 ID를 다시 쓸 때:** 앱이 `AI_RESPONSE`로 거절한다. 어떤 자료에도 없던 ID도 같다.
- **첫 답변 뒤 `b.ts`가 바뀌면:** 후속 질문은 `CHANGED`로 거절된다.
- **판단:** 잘못된 근거가 화면에 나오지는 않는다. 다만 모델이 이전 ID를 다시 쓰면 사용자에게는 오류로 보인다. 지시문에는 근거 범위 제한이 이미 있다: 코드 설명은 선택 근거나 `files`의 `evidence.id`로 뒷받침하고, 작업 정리에서는 이미 제공된 근거 ID만 쓴다. 하지만 앱은 이전 답변을 질문과 설명만 보내고, 그 안의 근거 ID가 이번에는 쓸 수 없다는 안내도, 그 ID가 어느 파일이었는지도 보내지 않는다.
- **고칠지는 사용자 결정 대기:** 그대로 두기, 지시문에 한 문장 더하기, 이전 답변의 파일 경로를 함께 보내기, 이전 답변의 파일을 앱이 자동으로 다시 읽기 중에서 고른다. 관련 파일 수·코드량·대화 보관 한도는 바꾸지 않았다.
- **확인하지 않은 것:** 실제 모델이 후속 질문에서 파일을 다시 요청하는지, 이전 ID를 다시 쓰는지는 실제 요청이 막혀 있어 미확인이다. 화면의 근거 이동은 기존 Electron 가짜 AI 검사(고정 ID)만 확인했고, 이번 시험은 앱 조회(`lookup`)까지 확인했다.
- 검증: `npx vitest run tests/ai-followup.test.ts` 4개 통과, `npm test` **16파일 285개** 통과, typecheck 종료 0.

[공식 CLI 권한 문서](https://antigravity.google/docs/permissions/)는 deny/ask/allow를 사용자 전역 `~/.gemini/antigravity-cli/settings.json`에서 설정하도록 설명한다. 현재 도움말과 [CLI 참조](https://antigravity.google/docs/cli/reference/)에서는 기존 인증을 유지하면서 앱 전용 설정과 전역 확장 차단을 함께 제공하는 경로를 확인하지 못했다. 전역 설정을 수정하거나 인증을 복사하지 않았으며, C04/C05 실제 AI 시험은 실행하지 않았다. 다음 선행 조건은 Antigravity의 앱별 설정·확장 격리 경로와 Codex의 스킬·플러그인·관리형 설정 상속 범위를 확인하는 것이다. 확인 후 비밀 없는 별도 시험 자료에서 범위 밖 접근 거부와 훅·MCP 미실행을 실행 기록으로 검증해야 한다.

다음 연결 작업은 **현재 계정 인증을 유지하면서 앱 호출만 제한하는 방법 확인 → 비밀 없는 시험 자료로 C04/C05 실제 차단 검증 → 두 실행기의 인증·JSON·취소 시험**이다. 기존 Codex → Gemini → Codex 흐름과 Gemini `gemini-3.8-flash-high` 방향은 유지한다.

관련 파일 읽기 요구를 반영하면서 macOS `sandbox-exec`로 원본 쓰기를 막는 방식도 별도로 시험했다. `scripts/ai-sandbox-smoke.mjs` / `npm run test:ai-sandbox`는 비밀 없는 임시 프로젝트와 scratch만 사용하며 네트워크를 막는다. 읽기 허용, 덮어쓰기·생성·삭제·이름 변경·chmod·자식 쓰기 차단, 외부 링크 읽기/쓰기 차단, scratch 쓰기, 원본 내용·메타데이터·목록 보존을 검사한다. 이것은 fixture의 OS 제한 검증이며 production CLI에 적용 완료했다는 뜻이 아니다. 현재 제한된 셸 내부에서는 nested sandbox가 허용되지 않아 정상 권한 확장으로 이 독립 시험을 실행했다.

Antigravity의 전역 설정·훅 읽기를 차단한 로컬 부팅에서 훅 0개가 로딩된 기록을 확인했지만, custom agent의 `tools: []` 적용과 기존 로그인 유지까지 확인하지 못했다. 외부망 차단 부팅은 `authentication required`로 끝났으며 `init.tools`도 받지 못했다. 최초 온라인 부팅 시험은 인증·접속 정보 전송 가능성 때문에 자동 승인 검토에서 거절됐다. 이후 사용자에게 프로젝트 코드 없는 기존 로그인 접속·초기 도구 확인 범위를 설명했고 명시적으로 진행 승인을 받았다. 승인 이후 결과는 아래와 같다.

### 사용자 승인 후 Antigravity 연결 시험

`test-results/antigravity-preflight.json`에 민감정보를 제외한 결과를 기록했다. 설치 CLI는 `agy 1.3.5`, 실행 설정의 모델 ID는 `gemini-3.8-flash-high`다. 모델 질문은 보내지 않았으므로 실제 응답 모델은 없으며 Gemini 답변을 사용한 작업으로 표시하지 않는다.

1. 외부 접속 허용 + 기존 인증 파일 후보의 제한적 읽기: 종료 1, `authentication required`, `init` 없음.
2. 공식 macOS Keychain 도구(`/usr/bin/security`) 실행 추가 허용: 같은 실패. 파일 쓰기는 임시 scratch만 허용하고 전역 훅·MCP 설정 읽기 차단은 유지했다.
3. 오류 기록에 나타난 `jetski_state.pbtxt` 읽기만 추가 허용: 같은 실패. 이 파일은 인증 전용이라고 확인되지 않은 앱 상태 파일이며 내용은 직접 열람하지 않았다.

세 시험 모두 stdin으로 질문·코드를 쓰지 않았고 `init.tools`를 받지 못했다. 따라서 **기존 로그인 복원·도구 차단 확인·실제 AI 연결은 실패/미검증 상태**다. 정상 환경의 기존 agy 로그인 자체가 없거나 만료됐다고 단정할 근거는 없다. 공식 문서는 [운영체제 로그인 보관함에서 기존 세션을 복원](https://antigravity.google/docs/cli/install/#local-silent-keyring-sign-in)한다고 설명하지만 이 앱의 제한 조건에서 성공시키지 못했다.

로그인 보관함 디렉터리 전체 읽기와 외부 접속을 함께 허용하는 후속 시험은 **자동 승인 검토에서 거절되어 실행하지 않았다.** 다른 서비스의 민감한 자격증명·세션 정보에 접근할 위험이며, 기존 로그인 접속 승인은 그 광범위한 접근까지 포함하지 않는다는 이유였다. 이를 우회하거나 보관함 데이터를 복사하지 않았다. 더 좁은 진단으로 네트워크 없이 `security list-keychains -d user`의 경로 목록 조회만 비교했고, 일반/제한 환경 모두 종료 0·경로 1개였다. 비밀번호·토큰 값은 조회하지 않았다.

시험 임시 경로로 식별되는 agy 프로세스는 종료 후 0개였다. 별도 daemon이 경로 표식 없이 살아남았는지까지 보장하는 검사는 아니다. `/usr/bin/security` 허용은 Keychain 읽기 전용을 강제하는 규칙이 아니므로 OS 파일 쓰기 차단을 Keychain 무변경 보장으로 설명하지 않는다. 앱 소스·설정과 production 전송 차단은 변경하지 않았다. 이번 변경은 시험 결과와 문서뿐이므로 기존 129개 테스트·GUI·패키징 검사를 불필요하게 재실행하지 않았다.

## 남은 기능과 보호 한계

- 현재 단계 목록은 구문 구조다. 기능 목적·시작/성공/실패의 쉬운 설명, AI 질문, 호출 관계 추적, 전체 문맥·다른 파일·이전 위치 복귀 동선은 아직 완료하지 않았다.
- 파일은 최대 256 KiB, 탐색은 1,000파일·5,000항목·깊이 20, 분석 출력은 파일 전체 1,000근거·200함수·20,000구문 방문으로 제한하고 일부 결과임을 알린다. worker 요청은 한 번에 하나·최대 30초다.
- 새로 추가된 파일 목록은 폴더를 다시 열어 갱신한다. watcher는 전체 프로젝트 실시간 색인이 아니며, 감시 실패·잠자기 복귀·재시작의 전체 회귀 검수는 남아 있다. 근거 사용 시 재검사를 적용했다.
- 파일명 기반 비밀 제외가 모든 비밀정보를 찾는 것은 아니다. 선택 코드·파일 목록·관련 파일·질문·최근 답변 전송 동의는 질문 화면에 구현했다. 소스 본문의 흔한 비밀값 형태는 전송 전에 가리지만(2026-10-15, 질문은 2026-10-17부터) 모든 비밀값을 찾지는 못한다.
- 경로·inode·해시 재검사는 적용했지만 Node의 portable `openat` 부재 때문에 악의적으로 상위 폴더를 동시에 교체하는 공격을 OS 수준에서 완전히 격리한다고 보장하지 않는다. 동일 사용자 권한의 악성 로컬 프로세스에 대한 전체 보호는 미검증이다.
- Python 분석·Java/Dart 전체 탐색 검수·프레임워크/설정 해석·지도·학습 기록/복원·Git 비교는 후속 단계다.
- 본인이 만들지 않은 자료로 하는 사용자 이해도 관찰, 실제 Finder/폴더 선택창 수동 검수, 잠자기/복귀, 성능 측정, Developer ID 서명·공증은 미실행이다.
